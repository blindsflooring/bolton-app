# Bolton Build Log

This is the permanent, narrative build history of Bolton — Blinds & Flooring
Studio's internal quoting/job-workflow app. It exists so Burgert (or any
future developer who inherits this codebase) has a real account of what was
built, why, and what's still open — not just a list of commit messages.

**Ongoing practice:** every future work session appends a new dated entry
here before the session is considered wrapped up. Reverse-chronological —
newest entry at the top.

For the pre-repo history (v1–v65, before this git repository existed), see
[`CHANGELOG.md`](../CHANGELOG.md) in the repo root — it was carried in as-is
at the very first commit and is the authoritative record of that earlier
period. This file picks up from the repo's actual creation (2026-08-19) and
continues forward from there, reconstructed from the real git commit
history (129 commits, 2026-08-19 → 2026-08-28) rather than from memory.

One new field (`Quote.installation_notes`), no new tables — materials-to-load sourced entirely from the job's real Order Sheets (never re-derived separately, so it can't disagree with them), plus reference notes pulled in from wherever they already exist on the system (`Client.notes`, the original Lead's notes if this job came from one) alongside a dedicated, editable notes section for anything specific to enter right before printing.

Fixed with a real hysteresis band. Confirmed with a quantitative test of the actual mechanism; **not** marked resolved — no working browser was obtainable in this session to visually confirm it, and Burgert hasn't confirmed it live yet either.
- **Master Workflow proposal, first two build-order items: Booking visibility fix + Decline Quote reason.** `_job_workflow_info()`'s "accepted" branch (Next Action) and `_job_steps()`'s scheduling step (the step strip) both now check `installation_date`/`installation_confirmed_date` — a tentative date already sitting on an accepted job now reads "Confirm installation — [date] proposed" / a step-strip note, instead of a plain "Book installation" that was blind to it ever being set. `decline_quote()` now takes a mandatory `reason`, writes it to `AuditLog` (no new field on `Quote`), and `get_quote()` reads it back so Job Detail's declined panel shows why, not just when.
- **Version badge fixed** — real `GET /version` endpoint (Render's own `RENDER_GIT_COMMIT` env var, set automatically on every deploy, plus a process-start timestamp captured fresh every restart), fetched on login. Replaces a hardcoded `"v65"` confirmed via `git blame` to have been literally unchanged since this repo's very first commit — 130+ commits and 9 days silently unreflected.
- **Sticky header flicker, third pass.** Burgert confirmed live on his phone that the hysteresis fix (previous pass, same day) didn't fix it — his repro is a single, plain, one-directional downward scroll, flickering right as the header shrinks, which rules out repeated toggling as the cause (a single clean class toggle only ever runs its transition once). Applied `will-change`/`translateZ(0)` to `#appHeaderWrap`, forcing early GPU compositing-layer promotion — the documented fix for a CSS transition running on/inside a `position: sticky` element during active touch-scrolling, a known Mobile Safari/Chrome flicker source independent of toggle count.
- **Header Flicker: real cause found on video, fourth pass.** Burgert sent two screen recordings (brief: "Bolton-Brief-Header-Flicker-Final.docx", fetched from his Downloads folder). Frame-by-frame analysis in the brief showed the actual on-screen behaviour for the first time this bug has been chased: the header TITLE TEXT genuinely flipping between fitting on one line and wrapping to three, repeatedly, within about a second of scrolling — a text-wrap width threshold with no safety margin, a different mechanism entirely from the previous two passes. Traced two concrete, self-inflicted width triggers: the logo's `height` scroll-compact transition let `width:auto` continuously recompute the image's rendered width as a side effect (~165px→~117px, confirmed by decoding the embedded PNG's real 340×70 dimensions) — fixed at a constant 165px with `object-fit:contain`; and the new version badge (this session's own version-fix change) popping in empty→populated on page load — given a fixed `min-width`. The title itself also got `white-space:nowrap`/`text-overflow:ellipsis`, removing the wrap-vs-no-wrap failure mode structurally rather than just narrowing its remaining triggers, since CSS has no native way to add real hysteresis to a text-wrap decision.
- **Header Flicker: static by design, fifth and final pass, same day.** The fourth pass's own fix introduced a new, worse regression the moment it went live: the header fully disappeared on scroll-down, reappeared on scroll-up — not spec. Per Burgert's direct, explicit instruction: stopped patching individual scroll-linked symptoms one at a time and removed the entire category instead. All scroll-linked header behaviour deleted — the `.scrolled` class, its scroll listener, every compact-on-scroll CSS rule, the padding/height transitions, and the `will-change`/`transform:translateZ(0)` GPU-layer-promotion hack from the third pass (very likely the actual cause of the new hide/show regression — a `transform` on the same element `position: sticky` depends on is a known way to break sticky positioning on some mobile browsers; removed along with everything else). The header now renders at one fixed size, always, and stays visible purely via native `position: sticky` — nothing about it reacts to scroll position or direction at all. The title's nowrap/ellipsis and the badge's fixed min-width (fourth pass) were deliberately kept — neither is scroll-linked, both remain valid protection regardless.

### Why (root causes, decisions, rejected alternatives)
- **Real, confirmed data-quality finding**: the same real supplier appears under three different exact strings in the live price book — `"Azura"` (floor-prep), `"Azura Distributors"` (most flooring material), `"Azura Distributors (iTe)"` (screed). The *old* hardcoded `if supplier == "Azura"` merge check could never have matched `"Azura Distributors"` — confirmed as the real mechanism behind a job showing two separate Azura sheets instead of one combined delivery. Fixed with a small, explicit, extensible alias list used *only* for the merge decision — never changes what's actually displayed or stored.
- **Real bug fixed**: `materials_ordered` was a checkbox with zero connection to whether an Order Sheet was actually placed — a real, live source of disagreement between what Next Action said and what had actually happened.
- Chose a general supplier-based merge rule over a hardcoded "Azura is special" case specifically because which suppliers cover multiple categories could change over time — a structural fix, not a one-off patch.
- **Phase 3 caught a real design gap before shipping, not after**: Phase 2's tiles only rendered while Procurement was the *active* step. Removing the old surfaces as originally planned would have made a job's Order Sheets completely unreachable once it moved to Scheduling — fixed by making the tiles persist for the whole life of the job.
- **Blinds explicitly excluded from this whole redesign**, per direct instruction — flooring gets built and proven end-to-end first; Blinds procurement tracking is deferred to its own later phase.
- On Hold deliberately kept as two nullable fields alongside `workflow_status`, never a 5th status value — matches the standing "no second status system" principle and the existing `declined_at` pattern.
- **Lead deliberately isolated from the Job workflow**, per the proposal's own risk assessment: a Lead only ever feeds INTO a Quote via `converted_quote_id`; nothing reads back. `_lead_next_action()` is a genuinely separate, smaller engine from `_job_workflow_info()` rather than a branch bolted onto it — merging the two would mix two different engines for two different stages.
- **The Robust Owner Delete startup completeness check did exactly its job**: adding `Lead.converted_quote_id` (a new FK to `quote.id`) failed app startup immediately with a clear message until a cascade policy entry was added — precisely the "can't reach production without a developer consciously deciding its policy" guarantee that check exists for. Policy chosen: `nullify` — the enquiry genuinely happened and is real history, so deleting the quote it converted into must not delete the Lead, only clear the backward-link.
- **Real bug caught before shipping** (not a live incident): the convert-to-quote endpoint's second `session.commit()` (saving the lead's new status) silently expired the already-refreshed `Quote` object still attached to that session — SQLAlchemy's default `expire_on_commit` — so the response briefly serialized the new quote as an empty `{}`. Fixed by re-refreshing it after that second commit too; caught by the project's own "verify end-to-end before pushing" discipline, not by a user report.
- No outcome-note field on Lead itself — every status change's note is folded directly into the existing `AuditLog.new_value` (`"contacted — Called 14:20, wants a site visit Thursday"`), reusing the general-purpose audit table rather than adding a parallel notes-with-timestamp mechanism, per the proposal's own explicit instruction.
- `visit_date` deliberately independent of `lead_status`, not a value or a side-effect of any status — a visit can be proposed while a lead sits in any non-terminal status, same "no second status system" discipline applied again.
- `site_address` was the *only* new field added for the day-list follow-up, not a broader address/detail rewrite — the brief's own "propose the smallest set... rather than guessing at an exhaustive list" instruction, and "what's needed" per lead on the printed list reuses the existing `notes` field rather than adding a redundant one.
- `_leads_for_day()` built as a standalone, reusable query and deliberately does NOT filter by `lead_status` — the brief explicitly frames this as a stepping stone toward a future calendar feature, where a calendar view would want to show every visit on a day regardless of outcome; status-based filtering/styling was kept a display-layer concern instead of baked into the data access.
- Since `lead` was already a live production table (created hours earlier the same day), the two new columns went through the `_ensure_new_columns()` migration list, not just a model change — added to both together this time, the exact discipline learned from the `documentarchive.is_accepted_version` incident (2026-08-27).
- Real bug caught before shipping: the day list's Print button originally serialized the day's lead data straight into an `onclick` attribute via `JSON.stringify` — a name or note containing an apostrophe or quote (e.g. "O'Brien Family") would have broken it. Fixed to read from a cached variable instead, same convention as `leadsCache`/`orderIndexQuotesCache` elsewhere in this codebase.
- **Needs Attention root cause, confirmed not guessed**: the brief's own hypothesis was "two different code paths" — checked directly by reading `list_quotes()`/`get_quote()` side by side, and ruled out: both already read the identical `_job_workflow_info()`, with `materials_ordered` already derived identically for both. The real defect was one level deeper — inside that single shared function, two genuinely different states (materials not ordered vs. ordered-but-receipt-unconfirmed) reused the identical `"Materials required"` label, so a job that had genuinely progressed still displayed as if nothing had happened. Fixed with a distinct label in the one already-shared function, per the brief's own "one source of truth" instruction — no second fix, no new code path introduced.
- Quote/Invoice Preview conditional logic reads `workflow_status` directly (the same field `_job_workflow_info()` already uses to decide "invoicing is relevant now") rather than a new flag — guarantees the preview pane can never disagree with what Next Action itself says.
- Order Sheet preview's Edit button question (raised explicitly by the brief as open) resolved by reading the actual behaviour rather than guessing: for `docType='ordersheet'`, Edit already just navigates to Order Sheet Detail — identical to what the tile's own click used to do — so there's no real inline-editing risk, and Edit was kept rather than dropped.
- Job Card's materials sourced entirely from Order Sheets, never QuoteLineItem directly — same "reuse the exact same data, so the two can never disagree" reasoning as the Order Sheet previews above; a known, deliberate consequence is a Blinds-only job showing no materials today, since Blinds never produces an Order Sheet at all (Job Workflow Design Proposal's own scope boundary) — not a bug, a future phase's problem.
- Job Card's action bar deliberately NOT the standard five buttons, per the brief's own explicit "confirm which actions genuinely apply, don't include all five out of habit": Edit excluded (view-only per the original proposal), Save/Dropbox-archival excluded (a Job Card is a regenerate-on-demand operational aid, not a document of record the way Quote/Invoice/Order Sheet are — archiving it properly would mean extending `ARCHIVE_CATEGORY_FOLDER` for comparatively little benefit), Mail kept (genuinely cheap, a plain mailto with no pre-filled recipient since "the installer team" has no stored contact record anywhere in this app).
- PaymentFollowUp entries deliberately excluded from Job Card's pulled-in notes despite being real per-job notes too — they're payment-chasing records, not installation information, and showing them on an installer-facing document would work against the same "operational, not commercial" principle the no-pricing constraint itself exists for.
- Order Index overflow: proposed before building, per that brief's own explicit gate — presented the row-growth analysis and two candidate approaches (kebab menu vs. responsive reflow), Burgert chose the kebab menu. One unified fix for desktop and mobile rather than two different treatments, since it solves both symptoms (horizontal scroll on desktop, wrapped-link clutter on mobile) with the same mechanism.
- **Sticky header flicker root cause, confirmed one level deeper than the earlier same-day fix reached, not assumed to be the same bug**: that fix was real and correct as far as it went (throttling how often the scroll handler ran per burst, confirmed then with its own quantitative test), but it never added hysteresis to WHAT the handler decided. A single shared threshold with no gap between "compact" and "expand" means fast, direction-reversing scrolling genuinely re-crosses that one pixel value across many separate frames — not a redundant-execution problem the earlier throttling fix could have caught, a genuine, correctly-computed toggle firing once per frame for as long as scrollY keeps crossing it, each one restarting the header's own CSS transitions before the last one settles.
- Ruled out, not skipped, the brief's other named suspect (Chrome mobile dynamic toolbar / `100vh` interaction) — confirmed by inspection that neither `#appHeaderWrap` nor `header` uses any `vh` unit; the only `100vh` usage anywhere in this codebase is the login/reset-password screens and a photo lightbox, none visible while scrolling the app itself.
- Also reviewed, per the brief's own instruction to check what changed later today: whether the new `.job-detail-preview` sticky element (added during today's Job Detail layout work) could be a new contributor. Ruled out — it's an independent sticky context further down the page with no shared threshold logic, and the brief's own reproduction wasn't Job-Detail-specific.
- **Booking visibility root cause, confirmed by inspection not guessed**: the Master Workflow proposal's own current-state audit had already found `installation_date` and `installation_confirmed_date` were genuinely two separate, already-correct fields — `installation_date` settable via the Job Details form alone, never touching `workflow_status` — so this was a UI/logic gap over a correct schema, not a data-model problem. Confirmed directly that `installation_confirmed_date` is only ever set inside `schedule_quote()`, together with the flip to `"scheduled"` — so while a job sits at `"accepted"` it's structurally always `None`, meaning `installation_date and not installation_confirmed_date` is exactly "a date's been proposed but not confirmed," checked explicitly rather than assumed so this keeps working even if that invariant ever changes. Deliberately does NOT flip `workflow_status` itself — only the existing "Confirm Installation — Book" action still does that, matching the proposal's own Test 4 ("tentative date must not auto-confirm").
- Decline Quote reason scoped identically to On Hold's existing pattern (`hold_quote()`) rather than inventing a new one: mandatory reason, one `AuditLog` row, no new field on `Quote`. Found by the proposal's own instruction to sweep the whole system for the "marked done, zero evidence" shape, not just check Leads — Complaints/Reworks/Repairs/Reinstalls don't exist in Bolton yet, so Decline Quote was the one real, live instance.
- `decline_reason` deliberately read back from `AuditLog` inside `get_quote()` (most recent `field=="declined"` row for that quote), never cached onto `Quote` itself — keeps the "no new field" constraint honest while still letting the declined panel show why, not just when. Correctly shows nothing for quotes declined before this fix shipped — no reason was ever captured for those, and none is invented.
- Version badge deliberately NOT another manually-bumped counter — that's exactly the mechanism that let it go stale for 9 days/130+ commits the first time. Derived instead from two things that are always real: Render's own deploy-time env var and a startup timestamp, neither of which anyone has to remember to touch.
- **Real mistake caught and fixed same-session, not left standing**: `get_version()`'s own docstring claimed "No auth" because the endpoint declares no per-endpoint `Depends()` — wrong, caught by actually curling the live endpoint (401, not 200) rather than trusting the assumption. The closed-by-default `require_auth` middleware (2026-08-20) covers every path not explicitly in `PUBLIC_PATHS` regardless of per-endpoint declarations — exactly the guarantee that middleware exists for. Not a functional bug (the one real caller, `showApp()`, only ever runs post-login), just a wrong claim in the comment, corrected once actually checked.
- Sticky header, third pass: also tried converting the logo's `height` transition to a compositor-only `transform: scale()` — reverted before shipping once it became clear that stops the shrunk image's layout space from actually being reclaimed, quietly working against the compact header's whole stated purpose ("more page fits above the fold on mobile"). A real regression traded for an unconfirmed gain, not worth it — left that transition exactly as it was.
- Ruled out repeated toggling as this report's cause by re-reading the actual JS: the hysteresis band means a single monotonic downward scroll only ever crosses the compact threshold once, so a single clean toggle firing its transition once was already the confirmed behaviour before this pass — the remaining candidate had to be something that happens even on ONE clean toggle, not something reintroducing multiple toggles.
- Fourth pass on the header flicker deliberately given real video evidence to work from, not another round of code-reasoning-only diagnosis — the brief itself frames it as "please watch it before touching any code." This is why it found a materially different, more specific mechanism (text-wrap oscillation) than either of the first two passes did, both built from code reading and simulated scroll-position math alone.
- CSS genuinely has no mechanism to give a text-wrap decision "hysteresis" (a buffer zone) the way the earlier scroll-threshold fix could — wrap-or-not is a binary the browser recomputes from available width with no memory of its previous state. `white-space:nowrap` + ellipsis was chosen over trying to further narrow the width triggers because it removes the SECOND LAYOUT STATE entirely, closing off the failure mode rather than just making it statistically less likely to trigger — including against a cause outside this codebase's control (mobile Chrome's own address-bar-driven viewport resize during scroll), which no amount of width-trigger-chasing here could ever fully rule out.
- `min-width:0` added to the h1's parent flex-item div specifically because flex items default to `min-width:auto`, which silently prevents a flex child from shrinking below its content's natural width — the exact CSS gotcha this codebase already has direct precedent for (Mobile Rendering Audit brief, 2026-08-26) — without it, `overflow:hidden`/ellipsis on the h1 would never actually engage.
- Static-by-design decision explicitly Burgert's own, not a default fallen into after running out of ideas — the brief instructed stopping the symptom-by-symptom pattern outright, given four separate scroll-linked fix attempts on one mechanism (shrink flicker → width-lock → badge-width → hide/show) had already accumulated. Trading away the compact-on-scroll visual polish for eliminating the entire bug category was an explicit, stated tradeoff, not a compromise reached by default.
- The hide-on-scroll-down regression's likely cause (not just guessed at, reasoned from a known, documented browser compatibility issue) — a CSS `transform` on the same element `position: sticky` is declared on can interfere with the browser's own sticky-positioning computation in some mobile implementations. This was added by the THIRD pass specifically (`will-change`/`translateZ(0)`, intended to fix the shrink-transition flicker via early GPU layer promotion) — its removal here is very likely the actual fix for the new regression, not merely incidental to the broader cleanup.

## 2026-08-27

### What shipped
- **Real, urgent bug fixed**: passwords silently reverting on every deploy. Three incident-remediation functions (`_old_password_still_works_remediation()` and two others) ran unconditionally on *every* startup and force-reset three real accounts back to one hardcoded historical password hash whenever the current hash didn't match — with no guard against a legitimate later change. Removed from `on_startup()`.
- **Database Backups** — daily/weekly automated Postgres backups (pg_dump preferred, pure-Python JSON fallback), stored in Dropbox, 7-daily/4-weekly retention with automatic pruning, plain-language restore documentation (`RESTORE_BACKUP.md`), a verification-only content preview so a real backup's contents can actually be inspected.
- **Dropbox long-lived refresh token** support, replacing the short-lived access token that required manual renewal.
- **Dropbox Document Archive v2** — extended the existing Quote-only archiving to Invoices and Order Sheets, plus a nightly Order Index CSV snapshot (new in-process APScheduler, since no scheduling infrastructure existed anywhere in the repo before this).
- **Dropbox folders flattened to per-branch** (`Bolton/Gansbaai/`, `Bolton/Hermanus/`, blank branch falling back to `Bolton/Unassigned/`) and a new **Send button** (Quotes/Invoices/Orders) opening the user's default mail client, with a clear "no email on file" message when there isn't one.
- **Standard Document Action Bar** — one shared View/Edit/Print/Save/Mail component across Quote/Invoice/Order Sheet, replacing three previously-inconsistent per-screen implementations. Order Sheet quantity edits are now genuinely enforced server-side once "placed" (previously UI-hidden only).
- Two **real production bugs found and fixed** in the PDF rendering pipeline while verifying the above: xhtml2pdf crashing outright (not a clean error) on `@keyframes`/`@media print` at-rules, and separately on CSS custom properties (`var(--x)`) — both had been silently 500ing every real archive call that sent the actual production stylesheet, for as long as archiving had existed.

- The Cloudflare edge-cache incident looked identical to the auth bug at first (mobile broken, desktop fine, "hangs then goes blank") but was a completely separate, coincidental issue — a transient 502 from a prior deploy got cached at the edge with a spoofed 200 status. Confirmed by directly comparing `cf-cache-status: HIT` (poisoned) against a cache-busted `MISS` (correct content) — evidence-first, not assumed to be the same bug as the one just fixed.
- Como import cascade: each of the five fixes addressed a real, distinct root cause rather than symptom-patching the same error message repeatedly — the frontend's outer timeout and backend's inner timeout were coincidentally identical (an exact tie, not a deliberate margin), `max_tokens` was tuned for the smaller sheets this feature was originally tested against, the extraction prompt never told the model to output compact JSON, and the zone-priced NOT-NULL bug was a real edge case the existing "never silently convert an ambiguous price" safety logic hadn't accounted for (a zone price is a directly-extracted real number, not a guessed conversion, so using it as a fallback isn't the same risk class that safety rule exists to prevent).

- **Sticky Supplier Console table headers** — three separate attempts before landing on a spec-correct fix; plus collapsible sections with per-browser memory, search-across-all-suppliers, and (later) genuinely screen-fixed scroll arrows with an `IntersectionObserver` handing off control between tables.
- Real column-alignment regression fixed (an import-work side effect had left existing-product rows one column left of their header) and a real horizontal-scroll-unreachable bug fixed (a global `table { width: 100% }` rule was silently capping the table instead of letting it overflow).
- A real markup-percent display inconsistency found and fixed — the raw stored value was always correct, but the Console showed it as a raw multiplier ("1.3") while the Floor Job builder showed the same number as "30.0%" elsewhere in the same app.
- **Owner Preview Mode ("View As")** — lets the real Owner preview the app as Sales/Admin, with genuinely stripped fields and blocked actions server-side (not hidden client-side), via one shared `get_current_role()` dependency nearly every endpoint already reads through.
- **Login & Session Activity Log, Phase 1** (session-level only — a feature-level breakdown explicitly flagged and deferred) — real logout now soft-ends a session rather than deleting the row, so there's an actual history to report.
- Real cost-leakage bug found and fixed during Owner Preview Mode regression testing: two stairwell-specific cost fields were stripped for Sales only at line-creation time, not when re-opening a saved quote — `get_quote`/`list_quotes` shared a stripping function that didn't yet know about those two fields.

### Why (root causes, decisions, rejected alternatives)
- Aspen pricing bug: confirmed the exact wrong-formula pattern held for every single one of the 35 products, no exceptions — verified against the real `calculate_flooring_line()` function, then live on the deployed backend, not just by inspection.
- AI Price Sheet Import deliberately never does unit conversion itself (per-box → per-m²) — extracts the raw price and its stated unit basis separately and leaves the conversion to a human reviewer, specifically to avoid repeating the exact shape of bug that caused the real Aspen price-book mix-up this project had already found and fixed once.
- `DATETIME`-vs-`TIMESTAMP` root cause: SQLite has no real type enforcement on column declarations, so it silently accepted an invalid type name in every local test — the bug was structurally invisible until it hit real Postgres. Every other type string in that same migration was then manually re-audited against real Postgres syntax rather than assumed safe by association.
- Sticky-header root cause (confirmed twice, across three attempts): setting `overflow-x: auto` on a wrapper div forces its computed `overflow-y` to `auto` too, per the CSS overflow spec — not overridable by also setting `overflow-y: visible` — which silently makes that div `position: sticky`'s containing block instead of the page, so a naively-applied sticky header parks at a fixed offset into the table rather than tracking real scroll. The final fix moved the header out of the scrolling wrapper entirely (a cloned header bar as a page-flow sibling) rather than fighting the spec.
- Column-misalignment bug traced to a real regression: the AI import work added a leading empty header cell for the "NEW (import)" indicator, but the renderer for *existing* products never grew a matching leading cell to match.
- Markup-display fix scoped deliberately narrow (exact field-name match, not a "multiplier" substring match) because `over_tiles_multiplier`/`removed_tiles_multiplier` are a genuinely different kind of multiplier (a screed job-type rate factor) where the raw "×1.5" display is already correct and shouldn't be touched.

### Deferred / parked (and why)

- Login & Session Activity Log Phase 2 (feature-level breakdown, not just session-level) — explicitly flagged as not built this pass.
