## The near-miss that nearly took Bolton down — resolved, but read it

**PR #43 is merged and deployed. Nothing is outstanding here. It is first in this
document because the lesson is the most valuable thing in it.**

PR #42 changed `analytics_overview` to use `Depends(require_owner)`:

```
require_owner        defined at backend/main.py line 5697
analytics_overview   used it at            line 3489
```

Default arguments evaluate at **import time**, so `main.py` raised
`NameError: name 'require_owner' is not defined` and the backend would not start.

That broken code sat on `main` for about two hours. Production stayed up only
because Render had not redeployed. It was caught while writing this handover,
fixed in #43, and Render then deployed the very next commit — the backend came up
on `84e3cc1` at 15:31 and is healthy. Had the order been reversed, Bolton would
have gone offline entirely.

### Why it was wrong as well as dangerous

Six lines below that signature, and there all along:

```python
# Checked in the body rather than via Depends(require_owner) for a
# boring but real reason: require_owner is defined further down this
# file, and a default argument is evaluated at import time, so
# depending on it here would crash the app at startup.

if role != UserRole.owner:
    raise HTTPException(403, "The Business Overview is only available to the Owner.")
```

So #42's stated reasoning — that the endpoint "answered whoever asked" and that
hiding the tile was the only thing in the way — was **wrong**. Business Overview
has been owner-only server-side all along.

**The 403 measured while verifying #42 came from this existing guard, not from
the change.** The verification passed, and it passed for the wrong reason. That is
worse than not testing, because it manufactured confidence in a change that would
have caused an outage.

What #42 genuinely achieved still stands, and it is not nothing: moving
`'business'` from `SALES_HIDDEN_TILES` to `OWNER_ONLY_TILES` is what actually
revoked **Madri's** access. The tile had never been hidden from Admin, so the
in-body guard was never what stopped her — she simply had a doorway Ryno didn't.

### #38 — The restore path actually works now

The highest-value open item since backups were built. Backups ran nightly and had
**never once been restored**.

The 19 September 02:00 backup was pulled from Dropbox, verified byte-identical
against Dropbox's own content hash, and restored into a throwaway Supabase
project (since deleted):

```
41 of 41 tables   ·   8 031 of 8 031 rows   ·   0 mismatches
86 indexes, 66 constraints
J-0023 came back whole — 55 bags screed, 5,4 m + 3,7 m trim, R74 081,88 deposit
```

Four things now documented that weren't known before:

1. **The documented Dropbox path was wrong.** Backups go to
   `/Apps/Bolton Archive 2/Bolton/Database Backups/`, not `/Bolton/Database
   Backups/`. The old path exists and holds one stale backup from 27 August —
   following the old docs during a real incident would have found that and none
   of the good ones.
2. **A successful restore reports ~583 errors.** A Supabase `pg_dump` carries
   Supabase's own `auth`/`storage`/`realtime`/`graphql`/`vault` schemas, which
   already exist and which `postgres` may not modify. Judge the restore by
   counting `public` tables and rows, *never* by whether it errored.
3. **`psql` is not on this machine** and the Supabase SQL editor can't ingest a
   13 MB dump. `backend/tools/restore_driver.py` does it with `psycopg2` alone
   and skips the psql meta-commands (`\restrict`, `\unrestrict`) that pg_dump 18
   emits.
4. **A restore is a reset, not a rollback.** That backup contains no financial
   statements, because they were loaded later the same morning.

### #40 — Completion date

## The blinds question, and why it wasn't a problem

Two briefs arrived about blinds jobs. Both premises turned out to be wrong, and
the investigation is worth not repeating.

**"Blinds jobs can't be closed."** They can. Proven end to end on a throwaway
database — a blinds-only quote goes `quoted → accepted → scheduled → completed`
with a completion date, through the same three endpoints flooring uses. None of
`accept_quote()`, `schedule_quote()` or `complete_quote()` reads `job_category`,
and the only place `is_blinds_only` appears in the workflow UI changes a *word*
("blinds" instead of "materials"), never a button.

Locked in by `backend/tests/test_blinds_lifecycle.py` — if a product gate is ever
added to that path, it fails.

**"11 blinds jobs are stuck at accepted, imported from the old system."** They
weren't imported, and they aren't stuck:

| | |
|---|---|
| Job numbers | J-0009 to J-0025 — Bolton's own sequence, interleaved with flooring |
| Accepted | 8–16 September 2026, **in Bolton** |
| Age at session end | 3 to 11 days |

Flooring jobs close in **3 to 11 days** from acceptance. So the *oldest* blinds
job sat exactly at flooring's own slowest, and most were well inside it. Blinds
are made to measure with supplier lead time on top.

**No blinds job had ever been closed simply because Bolton's blinds workflow was
about three weeks old and none had come due yet.** The first ones, accepted
8 September, are due around now.

No review screen was built. It would have been a screen for a problem that didn't
exist, and would have had Burgert entering "old system" dates for jobs quoted in
Bolton the week before.

**If genuinely old blinds jobs from the previous system do exist**, they are not
in Bolton's `quote` table — that needs establishing before anything is built.

## Stock arrival — already existed

The brief asked for a way to mark that ordered stock has physically arrived. It
was already there:

- **Field:** `Quote.ready_for_installation`
- **Control:** the *Mark Materials Received* button on the Work Flow panel
- **Who:** `PUT /quotes/{id}/materials` takes `tenant_id` and **no role
  dependency** — any logged-in staff member, exactly as asked
- **Visible:** green tick with an Undo on the job; the Order Index shows a
  `CHASE Nd` badge when stock is overdue

It is deliberately independent of `materials_ordered`, because ordering and
arriving are days apart and collapsing them produces false "ready" signals.

Nothing was built. Worth knowing it exists before anyone builds it again.

## J-0019's date — nothing wrong, my error

Flagged during the session as "completion date one day before acceptance". It
isn't:

```
accepted_at      2026-09-12T14:16:45     (a timestamp)
completion_date  2026-09-12              (a date, i.e. midnight)
```

Huis Lettie Theron was accepted at 14:16 and completed later the **same day** —
sensible for a job with no installation date, invoiced the same day, paid on

The "−1 days" came from subtracting a timestamp from a date. Date-to-date gives
**0**, which is the truth. **No change was made, and none should be** — editing

## Still open

### 1. Whether Bolton's startup reconciles an OLDER backup's schema — untested

The last untested piece of the restore path, and the one with real consequences.

`SQLModel.metadata.create_all()` and `_ensure_new_columns()` run at boot and
*should* add missing tables and columns to a restored database. Nobody has
pointed the app at one and watched.

The gap is real, not theoretical: the 27 August dump was missing **12 whole
tables and 78 columns** against the models three weeks later.

To test: restore an older backup into a throwaway project, point a local backend
at it, and see whether it boots and reconciles. Procedure is in
`backend/RESTORE_BACKUP.md`.

### 2. Ask Bolton has no dedicated API key

Ask Bolton is live and working, but sharing a key:

```
ai_configured  : true
ai_key_source  : ANTHROPIC_API_KEY      <- the shared one
```

The code already supports a dedicated key and prefers it —
`ASK_BOLTON_ANTHROPIC_API_KEY`, falling back to `ANTHROPIC_API_KEY`
(`backend/ask_query.py`, `ASK_KEY_VARS`). Nothing needs building.

**What's outstanding is a Render environment variable.** Set
`ASK_BOLTON_ANTHROPIC_API_KEY` on the backend service and Ask Bolton picks it up
automatically; `/ask-bolton/scope` will then report
`ai_key_source: "ASK_BOLTON_ANTHROPIC_API_KEY"`.

Worth doing because Ask Bolton's spend is then separable from the price-sheet
extraction feature's, and either can be revoked without killing the other.

### 3. Smaller, genuinely optional

- **Per-rep scoping in Ask Bolton is enforced by the validator, not the
  database.** A Sales query must read `quote` and filter on a bound
  `quote.sales_owner = :sales_owner`. The stronger form is an RLS policy keyed to
  a session setting. Designed, not built.
- **Outstanding balance isn't stored**, so Ask Bolton honestly refuses to report
  it. The fix is to store `total_incl_vat` and `amount_outstanding` on the quote,
  maintained on write, with the nightly consistency monitor asserting they still
  match `_quote_totals()`.
- **8 Dropbox archive rows** (4 failed, 4 pending) hang off entities that can't
  be enumerated through the API — deleted quotes, most likely. Burgert decided
  not to chase them. They keep `needs_attention` non-zero, so the nightly monitor
  will keep raising one standing row.
- **The 11 accepted blinds jobs** — operational, not code. Either they get walked
  through as they come due, or they're tracked elsewhere and should be closed
  out.

## Working notes for whoever's next

**Verify on the real thing, not the diff.** Several bugs this session were found
only by driving the deployed page: the drill heading disagreeing with its own
list, the Work Flow jump that didn't scroll, and the money sections rendering.
Every one passed inspection in the source.

**The browser caches aggressively.** Render serves the frontend with
`s-maxage=300`, and a stale bundle was twice mistaken for broken code. Check
`renderOrderIndexTable.toString().includes(...)` for what's *running*, not what
the server serves. Ctrl+Shift+R, and give the CDN five minutes.

**`/version` needs auth**, so `curl` gets a 401. A deploy check that reads 401 as
"not deployed" was one of this session's own false alarms.

**There is no CI.** No `.github/workflows` — a green PR means no checks are
configured, not that checks passed. Run these by hand:

```
python backend/tests/test_ask_query.py            # suites A-K, 64 adversarial queries
python backend/tests/test_blinds_lifecycle.py
node   frontend/tests/test_money_sections.js
node   frontend/tests/test_tile_permissions.js
```

**The recurring failure mode this week** — worth carrying forward, because it
appeared five separate times: *a system reporting success or failure about
something it never actually checked.* The Dropbox alert blaming a working
credential; a deploy check reading 401 as "not deployed"; Ask Bolton reporting
its own blind spot as a fact about the business; a backfill reporting success
against the wrong database; and the 403 in #42 that appeared to prove a change
which in fact broke the app (caught, fixed in #43, deployed). PR #36 swept the nightly jobs for this class. It's
worth asking of anything that reports a status: *what did it actually check?*
